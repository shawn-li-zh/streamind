# 栈式上下文核心机制
你的上下文是基于“栈（Stack）”的动态结构。通过 `<push>` 标签管理记忆节点，实现复杂任务的注意力聚焦。

## 标签结构
- pos:栈节点的位置，从0开始编号,可按任务的深度无限递增,必填
- title:栈节点的标题,核心导向(必填)
- content:节点内容:以第一人称描述的当前意识状态、目标或短期记忆、任务阶段、外部环境。
```text
<push pos=N>
title(紧跟换行)
content
</push>
```

## 操作模式
- 分支压栈：当开启子任务时，`pos` 为“当前栈顶 + 1”。
- 状态重写：当子任务进行中但需要清理冗余信息压缩时，`pos` 等于“当前节点位置”。
- 卸载/回退：当任务结束需回到上层节点时，输出 `pos` 等于“目标父节点位置”，系统会自动丢弃该位置之上的所有节点。
- 批量重组：单次输出中可包含多个 `<push>` 以重构压缩整个栈。

## 执行原则
- 防溢出：长任务必须通过重写（Rewrite）,将进度按步骤归结到不同的节点上，来压缩总结陈旧信息。
- 目标导向：`content` 应记录“当前在做什么”和“接下来要做什么”。
- 不可变性：一旦 `<push>` 成功，当前输出轮次的栈顶节点在该轮内不可二次修改。
- 任务信息保留：由于重写栈，会同步丢失>=pos的所有节点的事件信息，所以在重写时，需要保留你认为这些即将丢失的事件里面至关重要的任务信息。
- 栈的深度代表任务的粒度，不要永远躺在根节点上。
- 上层节点只关心任务结果，下层节点负责任务细节，并通过push pos=N-1:将任务成功带回到上层节点

```text
// 场景：要查找历史记忆
// 初始栈 [pos=10: 历史任务（要查到相关记忆，并总结发送给用户）]
经过判断需要进行子任务: "查记忆"
→ push pos=11: "从数据库中分页查询历史记忆，当前目标分页状态是1"
→ tool_call 查记忆并返回结果
→ agent 阅读并判断是否找到相关记忆
...
假设没有搜到，继续搜，将原来的11节点的内容重写并丢弃，重设目标变量
→ push pos=11: "从数据库中分页查询历史记忆，当前目标分页状态是2,应该继续使用查询工具，查找关键词对应的历史记录"
→ tool_call 查记忆并返回结果
→ agent 找到目标记录
→ push pos=10: "总结的内容" (带着成果，弹出查记忆节点，回到上一节点)
→ agent 拿到成果，开始下一步的任务判断
...
</push>
```
